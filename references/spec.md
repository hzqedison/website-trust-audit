# 需求澄清与五章 SPEC

仅当用户要求把需求澄清成 SPEC 时使用。把已确认内容、待回答问题和证据假设分开；不根据页面审计缺口推导产品工程约束。若输入不足，输出待确认项，不擅自填目标人群、目标值、负责人或产品方案。

按五章组织：

1. **Problem Statement**：问题、目标人群、使用场景、已知证据及仍待验证假设。
2. **Proposed Solution**：仅记已选择的方案；候选方案明确标为待决，不把评审建议写成批准事项。
3. **Technical Constraints**：仅列确认过的技术栈、CMS、发布、支付、埋点等实际约束；未知即写未知。
4. **Non-goals**：明确本期不处理的事项，需确认的边界标待确认。
5. **Success Criteria**：指标、定义/分母、事件归因、基线、窗口、目标值与验收方法；缺项用待确认，不编造数值。

用户回答数字只有在映射到具体问题和统计语义后才构成需求输入。视觉上的可信感不能替代下载、安装、付费结果。SPEC 的决策状态及负责人由业务负责人确认，不凭空分配姓名。
